**Improvement Options**

| Improvement | Primary Use Case | Implementation Steps | Notes / Impact |
| --- | --- | --- | --- |
| Conversational memory in responses | Let follow-up prompts reuse prior answers without re-searching | 1. Pull recent Q/A turns from DuckDB (`chat_history`, `retrieved_chunks`) before building the prompt.<br>2. Pass them into `generate_prompt_template` as an `extra_context` block.<br>3. De-duplicate overlapping citations to keep prompts small. | Turns follow-ups into genuine dialogue; reduces redundant web calls. |
| Rich history for query rewriting | Rewrite search queries using full dialogue context | 1. Update `query_rewriter` to include the last N user+assistant messages (content, not just roles).<br>2. Clip/summary older turns to stay within model limits.<br>3. Cache rewritten queries keyed by conversation UUID. | Sharper rewritten queries, especially when users say “use the previous answer.” |
| Conversation summaries & pinned facts | Handle very long chats while keeping context relevant | 1. After each turn, summarize the conversation into short “memory” entries stored in DuckDB.<br>2. Surface pinned facts (e.g., goals, constraints) in the prompt payload.<br>3. Offer a sidebar to inspect/edit the summary. | Keeps prompts lean and prevents drift in long agent sessions. |
| History recall UI | Quickly reuse a past answer as grounding | 1. Replace the sidebar select box with a searchable list (by keyword/date).<br>2. On selection, inject the stored response into the next prompt’s context automatically, instead of just replaying messages.<br>3. Show source URLs alongside each stored answer. | Manual retrieval of earlier answers becomes one-click. |
| Task-mode handling (compare, expand, transform) | Support “compare with last”, “rewrite that as email”, etc. | 1. Classify follow-up intent via a lightweight prompt or rule set.<br>2. Branch into custom templates per intent (comparison, transformation, elaboration).<br>3. Feed prior answer text as the primary context. | Makes the agent feel purpose-built for iterative research. |
| Local knowledge ingestion | Blend web results with user-provided documents | 1. Add a file uploader that pipes into `RetrievalEngine` via LanceDB.<br>2. Tag chunks with `conversation_uuid` for scoping.<br>3. Expose a toggle to include/exclude local corpora during retrieval. | Critical for enterprise or offline workflows. |
| Reliability & observability | Debug and monitor long-running sessions | 1. Wrap major steps with structured logging (timers, selected URLs, token counts).<br>2. Persist RunTree metadata in DuckDB (start/end timestamps).<br>3. Provide a “download trace” button feeding LangSmith when available. | Speeds up diagnosing slow or failed runs. |
| Source transparency upgrades | Increase trust in aggregated answers | 1. Show the top URLs with snippets before the final answer streams.<br>2. Provide hover-over citations highlighting matched text.<br>3. Store rendered citations alongside responses for later review. | Clearer provenance, easier QA on responses. |
| Automated test scaffolding | Ensure new retrieval logic doesn’t regress | 1. Stand up `pytest` with fixtures that mock Tavily/Brave responses.<br>2. Add snapshot tests for prompt templates and query rewriting.<br>3. Run tests via `poetry run pytest` in CI before merges. | Gives contributors confidence to extend agent behaviors safely. |

**Strategic Tracks**

| Track | Objective | Implementation Outline | Dependencies / Considerations |
| --- | --- | --- | --- |
| UI upgrade (HTML/CSS/JS) | Replace Streamlit with a lean web front-end while reusing retrieval pipeline | 1. Extract existing orchestration into a FastAPI/Flask backend that exposes chat + configuration endpoints.<br>2. Build a static UI (HTML templates + vanilla JS) that streams responses via Server-Sent Events/WebSockets.<br>3. Recreate sidebar controls for model/search settings and hook them to REST calls.<br>4. Polish styling with a lightweight CSS framework (e.g., Pico.css) or custom SCSS. | Requires session management for multi-turn chats; keep Streamlit running until parity is reached to avoid regressions. |
| Baseline agent (current stack) | Preserve existing workflow as a reference implementation | 1. Tag current Streamlit-based agent as "Baseline" in docs and UI.<br>2. Stabilize by adding smoke tests (CLI + Streamlit endpoints) and version-locking dependencies.<br>3. Capture demo recordings / performance benchmarks to compare against future agents. | Useful for regression testing once alternate agents ship; avoid major refactors here. |
| Local upload ingestion (LanceDB) | Let users ground answers on uploaded files stored locally | 1. Add file uploader endpoint; parse PDFs/CSVs via `pymupdf4llm` or similar.<br>2. Store chunks in LanceDB with metadata (`conversation_uuid`, tags).<br>3. Extend `RetrievalEngine` to merge LanceDB results with web search context based on toggles. | Watch for storage growth; provide management UI to purge or re-index uploads. |
| Tool-aware agent orchestration | Offer agents that can choose web, search, or local tools dynamically (LangGraph/Pydantic AI) | 1. Wrap Tavily/Brave/DuckDuckGo and LanceDB queries as callable tools with structured payloads.<br>2. Define LangGraph or Pydantic AI workflows that route between tools based on query classification.<br>3. Surface tool usage logs in the UI for transparency. | Needs clear fallbacks when APIs fail; align with LangSmith tracing for observability. |
| User memory system | Persist long-term preferences and context beyond a single session | 1. Design `user_profile` tables in DuckDB (or SQLite) keyed by user ID.<br>2. Capture explicit signals (tone, preferred sources) and implicit notes (prior summaries) into memo fields.<br>3. Inject memory snippets into prompt templates conditionally; allow users to view/edit stored memories. | Handle privacy/opt-in flow; cap token usage via summarization of older memories. |
| HuggingFace/SmolAgent integration | Add a third agent type leveraging HuggingFace's smolagents toolkit | 1. Package existing tools (search, retrieval, LLM) as smolagent-compatible functions.<br>2. Configure HuggingFace Inference or local models for execution.<br>3. Offer agent selection UI (`Baseline`, `LangGraph`, `SmolAgent`) and route sessions accordingly.<br>4. Document setup for HuggingFace tokens and local model downloads. | Ensure environment can run PyTorch/transformers; consider async orchestration so UI stays responsive. |
| Multi-modal inputs (images) | Accept image uploads alongside text queries | 1. Add `st.file_uploader` for images (PNG, JPEG).<br>2. Base64 encode and pass to LiteLLM for vision models (GPT-4o, Gemini).<br>3. Add UI indicator when image is attached to query. | Requires vision-capable models; consider image size limits for token cost. |
| MCP Client support | Dynamically connect to external tool servers via Model Context Protocol | 1. Implement MCP client in `pravah/tools.py`.<br>2. Allow configuration of MCP server endpoints in `config.yaml`.<br>3. Register external tools dynamically at startup. | Enables plugin architecture; reduces hardcoded tool definitions. |
| Voice mode | Accept voice input and provide audio responses | 1. Use `st.audio_input` for recording.<br>2. Transcribe via Whisper (local or API).<br>3. Stream text response as TTS (optional). | Adds accessibility; requires audio processing dependencies. |
| Eval-driven development (EDD) | Run evals as part of CI/CD pipeline | 1. Add GitHub Action to run `scripts/eval.py` on PRs.<br>2. Fail builds if happy_path pass rate drops below threshold.<br>3. Store eval diffs for review. | Prevents regressions; requires eval dataset maintenance. |
